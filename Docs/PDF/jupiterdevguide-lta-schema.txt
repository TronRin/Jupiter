.LTA Exchange File Format
The .LTA (LithTech ASCII) exchange file format provides a format for describing structured data. It enables precise
communication of information between the LithTech tools (DEdit, ModelEdit) and the data packers for conversion to
platform specific binary files. LithTech uses the .LTA file format as the description format of worlds and models that are
used by the tools. The .LTA files are then translated to a platform specific binary format for the engine.
Note: The .LTA format can be compressed into the LithTech Compressed format (.LTC). To compress a file into an .LTC
file in your code, set the SaveNode function’s bCompress parameter to true as explained in the LTA Library section
below.

By extending the .LTA format, game developers can define an unlimited set of customized nodes for their own
communication needs. They can extend the current tools or create their own. An .LTA node can declare its associated
data to be a spatial coordinate, the name of a weapon, a skin’s identification, the shininess of an object, geometric
information about a model, or any other desired data.
LithTech includes an extensive .LTA reference for both the Model and World schemata.
Structure
Fundamentally, the .LTA format is a collection of lists delineated by parentheses. Values are the members of these lists.
The collection can be organized hierarchically by having one collection be a member of another collection.
The format’s simplicity makes it easy to parse, and its inherent hierarchy makes it easy to transform into internal data
structures.
An .LTA file is composed of a nested list of parenthetical nodes. The following example shows an .LTA file consisting

Syntax
The .LTA format recognizes all characters. Reserved characters include:
•
parentheses
•
quotation marks
•
spaces
Parentheses delineate the hierarchical structure of the list. Quotation marks contain string values. Spaces delimit
values. All other characters are free for use in strings, types, and values.
There are no escape characters for the reserved characters. Using the reserved characters in a value or type will
break the .LTA file.
The .LTA format is case-sensitive.
All values in an .LTA file are treated as strings. Values with quotes around them are tagged by the parser as being true
strings. The parser builds a parse tree, which retains all the values as strings with quoted strings tagged.
Node
An .LTA node consists of an open parenthesis, a close parenthesis, and the information between the parentheses.
Each node may contain any type of ASCII data, such as alphanumeric values, strings, and also other nodes. The
following example node contains four separate datum:
( superhero “Nigel” 934.97 ! )
A node that contains another node is called a list node (it is also a parent node). The inner node is the child node,

Schema
The .LTA format does not define any default types or tags. Only the hierarchical structuring tags are defined by the .LTA
format. The .LTA format can be extended to create .LTA schema. An .LTA schema is a description of an entity using the
.LTA format. Each schema will have its own “types” of nodes, permissible values, and hierarchy.
For examples of schemata, see the Model Schema LTA Reference and World Schema LTA Reference chapters of this
document. The therein are used by the ModelEdit and DEdit tools, respectively, to communicate model and world data
between the tools and the LithTech compilers.
Extending the .LTA File Format
You can extend the .LTA exchange file format by creating a new schema and an associated parser (reader and writer).
After the schema has been designed, the .LTA reader and writer can be coded to properly parse it. If you alter the
schema after the parser has been coded, you will have to update the reader for the new schema. The reader can check
for older format types, and provide a warning. As long as the writer no longer writes to the old format, one format can be
migrated into another.
Designing .LTA Schemata
The .LTA schemata define nodes, symbols, and hierarchies. The format provides freedom on how to design a schema.
Some suggestions are given below. There are, of course, many different ways to design a schema.
When designing an .LTA schema, keep in mind containment and hierarchical relationships. The .LTA nodes are their
own scope. Named nodes within other nodes are unique. For example,
(foo (bif foo))

Both foo can be treated differently since the second foo belongs in the bif scope and the first foo belongs in its
parent scope (which in this case is the global scope).
Nodes contain symbols and other nodes. Symbols can be used to define the type of the node. For example, if a
node will contain data about a superhero, the first symbol of the node can define the “type” of node.
(superhero)
Symbols can also contain strings. Strings can be used to identify a specific instance of a node. For example, the
second symbol in a node can be a string identifying the specific node.
(hero-name “Sunburst”)
When designing the node hierarchy, logical relationships should be devised. For example, if a node sets the powers
of a superhero, then the powers node can be a child of the superhero node.
(superhero
(powers
(flight passive body)
) )
Nodes can contain any number of symbols. While some symbols might define the type of the node, and others
might be strings identifying the node, at some point the value of the node will need to be set. One way to set a value is
to use a second symbol in the node. The example below sets the superhero’s primary stats:
(superhero
(primary-stats
(strength 12)
(agility 30)
(vitality 17)
(intellect 14)
(will 10)
(charm 18)
) )
Symbols might also be optional. The parse logic of an extended .LTA reader might use the exclamation point as a flag
to indicate that the node is in an “enraged” mode. The reader can define a set of node types that allow the flag.
(superhero !
) (hero-name “Sunburst”)
For ease of reading, explicit nodes are best. For example, to explicitly define a superhero’s attributes, the following
node hierarchy might be designed:
(superhero

tree. A Writer must be made to translate the internal data into the .LTA file by creating a parse tree that is saved to a file.

also needed to turn that format into an .LTA file.

Small Files
Small files can be kept in memory and interpreted in memory. Files like the superhero data files can all be kept in
memory until used.
Very Large Files
Large files, ones that are larger than one meg on disk should be evaluated as its being read in. Larger files need to be
read in pieces, and one unit is read in that unit is truncated from the tree.

The Parse Tree
The parse tree is the in-memory representation of an .LTA file. The .LTA parser constructs this tree as the file is read. It is
useful to understand the in-memory structure of the .LTA file so that you can understand how the reader works. The
most basic reader steps and searches through this tree to find needed information.
Given an ASCII .LTA file looks like this:
(foo (bar (a b) 2.0))
Then in memory the parse node structure looks like this :
lta_node->children[0]->value = “foo”
->children[1]->children[0] = “bar”
->children[1]->children[1]->children[0] = “a”
->children[1]->children[1]->children[1] = “b”
->children[1]->children[0] = “2.0”
Notice that the top node is a container. Its first member is an atom that contains the value foo. The second child of
that container is another container. This container has three children with the values foo, container, and 2.0.
All values are held at the leaves of this parse tree. These values are still strings when the reader gets the parse tree.
CLTANode
This class represents the nodes of an .LTA parse tree. As the .LTA file is read into memory, a parse tree is constructed.
Each node in the tree is a CLTANode instance.
CLTANode data members are all private for portability. All values for the data members are strings.
The CLTANodes represent lists, atoms, and nils. A list is a node that has children. An atom is a node that contains
one or more symbols but no children (a leaf node). A nil is a node that has no children and contains no symbols.
This class is defined in the LTANode.h header file and exposes the following functions:
AllocateElements Specify the number of child nodes for this node. Each child node must be set prior to using this
node.
AppendElement Append a CLTANode pointer to the list of child pointers for this node. This method is used in the
.LTA reader when the parser is filling in a list node. This should not be used frequently since it requires the
resizing of the internal arrays, and can cause a large performance hit. Instead, the node should call
AllocateElements with the proper size, and then set each element.
CLTANode( ) Construct a new atom node with no value (a nil).
CLTANode (uint32 nNumElements) Construct a list node. The nNumElements parameter sets the number of child
nodes.
CLTANode(const char* pszValue, bool bString) Construct a new atom node. The pszValue parameter is the value.
The bString parameter indicates whether the internal type is a true string.
Free Remove and frees all descendents of this node.
GetElement Return the parse node at a given index (0 based). This will return null if there is no element at the index.
This should only be used on lists.
GetValue Return a pointer to the value of this CLTANode. This can be converted to a number if a number is expected.
The value does not contain quotation marks, even if it is a true string. Use IsString to determine whether or not
the value is a true string.

CLTANodeBuilder class
This class builds .LTA parse trees. It is defined in the LTANodeBuilder.h header file and exposes the following functions:
AbortBuild Abort the build process. Deletes all nodes that have already been created.
AddElement Add an element to the current node on the stack. This assumes that the pElement parameter was
created with new. The new element instance is orphaned by the caller, meaning that any pointers to the
instance are invalid after this call.
AddValue Add a value node as a child to the list that was most recently pushed onto the stack. The four versions of
this function support double, Boolean, integer, and string values.
DetachHead Detach the parse tree currently being built. This pops all nodes off the stack and clears all memory
associated with the builder. This should be called only when the tree building process is completed. It is the only
method of obtaining the root element of the tree. The returned node must be deleted by the caller.
Free Free all memory associated with the CLTANodeBuilder instance. Use this when memory is critical and the
program cannot wait until the instance is destroyed.
GetDepth Return the current depth of the stack.
Init Initialize the builder. Should be used between building two parse trees to reset the builder.
Pop Remove the last element pushed onto the stack and create a list node instance. This new list node instance is
added to the list of children of the last CLTANode instance pushed on to the stack.
PopAll Remove all nodes from the stack. This ends the build process.
Push Push a new node onto the parse tree stack. This is similar to the opening parenthesis in an .LTA file. This will
cause a list node object to be created when the new node is popped off the stack. It will contain all the node
elements created after the push, until Push is called again.
Push(const char* pszValue, bool bString) Another version of the Push function. In addition to doing the push a
value (pszValue) is added to the list as the first element.
CLTANodeReader
Provides utility functions for loading entire parse trees or parts of parse trees. This class is defined in the
LTANodeReader.h header file and exposes the following static functions:
LoadEntireFile Open the specified file and load the entire file into a node tree.
LoadNode Parse through the current tree until a value matching pszStartString is found. Then create a root node and
add the value to it. It will then parse through the file until the list is properly closed. This can be used to pull
certain sections of a file out. Note that this is sequential, and if you want to back up, the file should be closed
and reopened. Another thing to note is that this value must come after an open parenthesis. So, (a, b) with
LoadNode("b") would return NULL, since the b does not come after the open parenthesis.

CLTAUtil
CLTAUtil is a collection of odds and ends functions that can aid in the traversal of lists. It contains helper functions, all
static, to determine information about files, and perform searching on lists.
IsFileCompressed Given a filename, this determines if the file is compressed or not.
GetMemoryUsage Given a node, this determines the amount of memory being used in bytes by the node and all of
its children
ShallowFindList Searches through a node and looks for a list that has the first element set to the specified value. Very
useful for finding keys in a list of children.
FindList Searches through a node and looks for the first list to have an element as the first item with a string that
matches the specified value. This will search into the tree recursively, meaning that all the children of the passed
node will be searched, then all of its children, and so on.
FindAll Builds up a list of all the lists that have the first element set to the specified value. Returns the number of
elements added below the specified start node
